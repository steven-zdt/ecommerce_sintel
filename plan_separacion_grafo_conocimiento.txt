# PLAN MAESTRO DE SEPARACIÓN

# PROJECT KNOWLEDGE GRAPH

## Extracción del Grafo de Conocimiento del Proyecto desde `ecommerce_sintel/ai_engine`

**Proyecto:** SINTEL E-Commerce
**Origen actual:** `ecommerce_sintel/ai_engine`
**Destino propuesto:** `ecommerce_sintel/project_knowledge_graph/`
**Tipo:** Módulo independiente de inteligencia estructural del proyecto
**Estado:** Plan de ejecución
**Fecha:** 2026-08-08

---

# 1. OBJETIVO

Separar completamente del `ai_engine` todos los componentes cuya responsabilidad sea:

> analizar, representar, consultar, relacionar y calcular dependencias estructurales del proyecto SINTEL.

El resultado será un módulo independiente:

```text
ecommerce_sintel/
│
├── ai_engine/
│
└── project_knowledge_graph/
```

El nuevo módulo será responsable exclusivamente del conocimiento estructural del proyecto.

---

# 2. DECISIÓN ARQUITECTÓNICA

El `AI Engine` ya no será propietario del grafo del proyecto.

La arquitectura queda:

```text
                    SINTEL PROJECT
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
   PROJECT KNOWLEDGE GRAPH       AI SUPPORT
             │                       │
             │                       │
       ┌─────┴──────┐                │
       │            │                │
       ▼            ▼                ▼
 PROJECT_MAP     KNOWLEDGE       LangGraph
                  GRAPH           Support
       │            │                │
       └──────┬─────┘                │
              ▼                      │
      DEPENDENCY GRAPH               │
              │                      │
              ▼                      │
       Impact / Blast Radius         │

Son dos responsabilidades diferentes.

---

# 3. RESPONSABILIDAD DEL NUEVO MÓDULO

`project_knowledge_graph` será responsable de:

```text
PROJECT KNOWLEDGE GRAPH
│
├── Descubrimiento del proyecto
├── Auditoría estructural
├── PROJECT_MAP
├── Knowledge Graph
├── Dependency Graph
├── Relaciones entre entidades
├── Blast Radius
├── Impact Analysis
├── Consultas estructurales
├── Reindexación
├── Actualización incremental
├── Versionado de snapshots
└── Validación de consistencia
```

No será responsable de conversación.

No será responsable de soporte.

No será responsable de memoria conversacional.

No será responsable de modelos LLM.

No será responsable de ChromaDB/RAG conversacional.

---

# 13. GRAPH QUERY API

El nuevo módulo debe tener una API Python clara.

Ejemplo conceptual:

```python
graph.get_node("shop.Product")

graph.neighbors("shop.Product")

graph.dependencies("shop.Product")

graph.dependents("shop.Product")

graph.impact("shop.Product")

graph.find_path(
    "shop.Product",
    "frontend_shop.ProductDetail"
)
```

El objetivo es que los consumidores no tengan que leer directamente JSON.

---

# 14. NO USAR JSON COMO API INTERNA

Actualmente varios componentes leen directamente:

```text
PROJECT_MAP.json
KNOWLEDGE_GRAPH.json
DEPENDENCY_GRAPH.json
```

Eso debe cambiar.

El nuevo módulo debe encapsularlos:

```text
Consumer
   ↓
ProjectKnowledgeGraph
   ↓
Repository / Snapshot
   ↓
JSON
```

Así podremos cambiar posteriormente el almacenamiento sin romper consumidores.

# 22. REGLAS ARQUITECTÓNICAS

## Regla 1

`project_knowledge_graph` es independiente de `ai_engine`.

## Regla 2

El AI Support no genera ni administra el grafo.

## Regla 3

El grafo no depende de LangGraph.

## Regla 4

El grafo no depende de Redis conversacional.

## Regla 5

El grafo no depende de ChromaDB.

## Regla 6

El grafo no necesita un LLM para construir las relaciones estructurales básicas.

## Regla 7

`PROJECT_MAP` es la entrada estructural.

## Regla 8

`KNOWLEDGE_GRAPH` representa entidades y relaciones.

## Regla 9

`DEPENDENCY_GRAPH` representa impacto y dependencias.

## Regla 10

Todos los artefactos de una generación deben compartir versión.

## Regla 11

No permitir snapshots obsoletos sin advertencia explícita.

## Regla 12

Los consumidores deben utilizar APIs Python del módulo, no leer JSON directamente.

## Regla 13

La auditoría debe ejecutarse desde el contexto correcto del proyecto.

La documentación actual registra un problema real: ejecutar `auditor.py` dentro del contenedor puede hacer que encuentre cero apps/modelos/endpoints porque su `BASE_DIR` está calculado para el árbol del host. Ese comportamiento debe corregirse durante la extracción para que falle explícitamente si el proyecto fuente no está disponible.

# 23. CRITERIO DE ÉXITO

La separación será considerada terminada cuando:

```text
ecommerce_sintel/ai_engine
```

pueda arrancar sin cargar:

```text
PROJECT_MAP
KNOWLEDGE_GRAPH
DEPENDENCY_GRAPH
```

directamente desde su propio directorio.

Y:

```text
project_knowledge_graph
```

pueda ejecutar:

```bash
project-graph audit
```

y producir:

```text
PROJECT_MAP
KNOWLEDGE_GRAPH
DEPENDENCY_GRAPH
```

de forma autónoma.

Además:

```text
GraphImpactAnalysisTool

debe seguir funcionando utilizando exclusivamente el nuevo módulo.

# 25. PRIMER PASO QUE DEBES EJECUTAR

**No recomiendo comenzar moviendo archivos.**

Primero hay que hacer una auditoría física del repositorio:

```text
ecommerce_sintel/
ai_engine/
```

y producir:

```text
PROJECT_KNOWLEDGE_GRAPH_INVENTORY.md
```

con esta información para **cada archivo relacionado**:

| Archivo                   | Responsabilidad  | Importado por | Lee         | Genera    | Consumidores | Destino                   |
| ------------------------- | ---------------- | ------------- | ----------- | --------- | ------------ | ------------------------- |
| `project_map.py`          | consulta mapa    | ...           | PROJECT_MAP | —         | ...          | `project_knowledge_graph` |
| `knowledge_graph.py`      | genera KG        | ...           | PROJECT_MAP | KG        | ...          | `project_knowledge_graph` |
| `dependency_graph.py`     | impacto          | ...           | KG          | DG        | ...          | `project_knowledge_graph` |
| `incremental_updater.py`  | actualización    | ...           | hashes      | mapas     | ...          | `project_knowledge_graph` |
| `auditor.py`              | pipeline         | ...           | source      | múltiples | ...          | dividir                   |
| `GraphImpactAnalysisTool` | consulta impacto | ...           | DG          | —         | AI Support   | adaptar                   |

**Ese inventario es obligatorio antes de la extracción**, porque la documentación confirma las responsabilidades generales, pero no proporciona el grafo completo de imports del checkout físico actual. Por tanto, no sería correcto afirmar todavía que esos son *todos* los archivos afectados.

```text

                       │

                       │

El estado documentado ya justifica esta separación porque el grafo tiene builders, artefactos, consultas, impacto y consumidores propios suficientemente definidos.
