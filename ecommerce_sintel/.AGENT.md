## [CRITICAL] 0-A. Auto-reload Django en Docker/Windows — inotify no funciona

**PROBLEMA:** Daphne (ASGI) no tiene auto-reload incorporado. Los volúmenes Docker
montados desde Windows/WSL2 no soportan inotify, por lo que cualquier cambio en
archivos `.py` — especialmente archivos nuevos — no se detecta. El servidor sigue
sirviendo el codigo viejo hasta que se reinicia manualmente.

**SOLUCION PERMANENTE (ya implementada):**
- `watchdog` instalado como dependencia en `pyproject.toml`
- `entrypoint.sh` envuelve Daphne con `watchmedo auto-restart --debug-force-polling --interval=2`
  cuando la variable de entorno `DEV_RELOAD=true`
  (la flag correcta en watchdog 4.x es `--debug-force-polling`, no `--poll`)
- `docker-compose.yml` ya incluye `DEV_RELOAD: "true"` en el servicio django

**CUANDO APLICA:**
- Al crear un archivo `.py` nuevo (nueva app, nuevo módulo, nuevo ViewSet, etc.)
- Al modificar cualquier archivo `.py` existente

**FLUJO CORRECTO cuando se agrega una nueva dependencia a pyproject.toml:**
```
docker compose build django   # reconstruye imagen con la nueva dep
docker compose up -d django   # reinicia con watchmedo activo
```

**SI el servidor sigue sin detectar cambios** (muy raro una vez watchmedo activo):
```
docker restart ecommerce_sintel_django
```

**PARA PRODUCCION:** Establecer `DEV_RELOAD=false` o eliminar la variable del entorno.
`watchmedo` no debe correr en producción.

## [CRITICAL] 0-D. Contenedores -> host: `host.docker.internal`, nunca `localhost` (incidente 2026-09-25)

- **[OBLIGATORIO]**: Toda URL que un contenedor use para llegar a algo que corre en el host (LM Studio :1234, Ollama nativo :11434, etc.) es
  `http://host.docker.internal:PUERTO`. `localhost`/`127.0.0.1` dentro de un contenedor es el propio contenedor. Las apps del host muestran
  `localhost` porque lo ven desde su lado: no copiar esa URL. Servicios del compose: usar su nombre (`http://sintel_ollama:11434`).
- **[OBLIGATORIO]**: en `docker-compose.prod.yml`, todo servicio que deba llegar al host declara `extra_hosts: ["host.docker.internal:host-gateway"]`
  (hoy `django`, `sintel_ai`, `sintel_ai_adk`), sobre todo si define `dns:` publicos (con ellos ese nombre no resuelve).
- **[OBLIGATORIO]**: al diagnosticar "no conecta con LM Studio", mirar primero el log de LM Studio: si la peticion no aparece, el fallo es red/URL, no el modelo.
- **Guardas en codigo**: `AIProvider.clean()` rechaza URLs loopback (`AI_PROVIDER_ALLOW_LOOPBACK`), el formulario avisa en vivo y el ADK descarta entradas loopback.
- **RAZON / detalle**: `AUDITORIA/INCIDENTE_IA_CONFIG_LOCALHOST_2026-09-25.md`.

## 1. ARQUITECTURA GENERAL

### 1.1 Stack Tecnológico

**Backend:**
- Django 5.2.13 + Django REST Framework (DRF)
- PostgreSQL como base de datos principal
- Redis para caché y broker de Celery
- Celery para tareas asíncronas

Todo modelo de negocio DEBE heredar de `SintelBaseModel`:

```python
# ecommerce/base_models.py
class SintelBaseModel(models.Model):
    uuid       = models.UUIDField(default=uuid.uuid4, editable=False, unique=True, db_index=True)
```

**Regla:** Nunca usar `pk` directamente en URLs. Siempre exponer y operar con `uuid`.

## 2. PATRÓN SERVICE LAYER (OBLIGATORIO)

### 2.1 Commands (Escritura)

Toda operación de escritura (create, update, delete) DEBE estar en una clase `*Commands`, nunca en las vistas.

```python
# services/commands.py
class ProductCommands:

    @staticmethod
    @transaction.atomic
    def create_product(vendor, category, name: str, price, **kwargs) -> Product:
        """Crear producto y variante por defecto en una transacción."""
        product = Product.objects.create(vendor=vendor, category=category, name=name, **kwargs)
        ProductVariant.objects.create(product=product, price=price, is_default=True, stock=0)
        return product

    @staticmethod
    @transaction.atomic
    def delete_product(product: Product) -> None:
        """Soft-delete: nunca borrado físico."""
        product.is_active = False
        product.save()
```

**Reglas obligatorias:**
- Siempre `@staticmethod` + `@transaction.atomic` en operaciones multi-tabla
- Retornar el objeto creado/modificado (no `None` salvo en delete)
- Nunca mezclar lógica de negocio con lógica de presentación
- Las vistas DEBEN re-fetch el objeto después de creación si necesitan anotaciones

### 2.2 Selectors (Lectura)

Toda consulta a base de datos DEBE estar en una clase `*Selector`.

```python
# services/selectors.py
class ProductSelector:

    @staticmethod
    def list_active() -> QuerySet:
        return (
            Product.objects.filter(is_active=True)
            .select_related('category', 'brand')
            .prefetch_related('variants', 'images', 'variants__images')
            .annotate(avg_rating=Avg('reviews__rating'), review_count=Count('reviews'))
        )

    @staticmethod
    def get_by_uuid(product_uuid: str) -> Product:
        return get_object_or_404(ProductSelector._get_detail_queryset(), uuid=product_uuid)
```

**Reglas obligatorias:**
- Siempre optimizar con `select_related` y `prefetch_related`
- Usar `.only(*FIELDS)` en listados para evitar cargar columnas innecesarias
- Anotar campos computados en la query, no en Python
- Separar querysets para admin (todos) y público (solo activos)

### 2.3 Estructura de Archivos de Services

```
{app}/
└── services/
    ├── __init__.py      # Re-exporta: from .commands import ...; from .selectors import ...
    ├── commands.py      # Escritura: Create, Update, Delete
    ├── selectors.py     # Lectura: List, Get, Filter
    ├── calculator.py    # Lógica pura de cálculos (si aplica)
    └── summary.py       # SummaryProvider para marketing (si aplica)
```

### 3.5 Regla Critica DRF: `@action` Solo Dentro de ViewSets

Los decoradores `@action` de DRF SOLO son registrados por routers cuando el metodo
pertenece a una clase `ViewSet`/`GenericViewSet` registrada en `DefaultRouter`.
Si se coloca un metodo con `@action` dentro de una `APIView`, Django compila sin error
pero el endpoint NO existe y el frontend recibira `404 Not Found`.

Caso real corregido el 2026-06-27:
`POST /api/v1/renting/rental-requests/{uuid}/process-payment/` devolvia 404 porque
`process_payment()` estaba indentado dentro de `RentalRequestListCreateAPIView`, no
dentro de `RentalRequestViewSet`.

```python
# INCORRECTO: APIView no registra @action en el router
class RentalRequestListCreateAPIView(APIView):
    @action(detail=True, methods=['post'], url_path='process-payment')
    def process_payment(self, request, uuid=None):
        ...

# CORRECTO: el ViewSet esta registrado en DefaultRouter
class RentalRequestViewSet(mixins.ListModelMixin, mixins.RetrieveModelMixin, viewsets.GenericViewSet):
    lookup_field = 'uuid'

    @action(detail=True, methods=['post'], url_path='process-payment')

        ...
```

Checklist obligatorio al crear o mover acciones custom:
- [ ] Confirmar que el metodo `@action` esta indentado dentro del `ViewSet` registrado.
- [ ] Confirmar `router.register(r'resource', ResourceViewSet, basename='resource')`.
- [ ] Confirmar que `lookup_field = 'uuid'` coincide con la URL usada por frontend.
- [ ] Ejecutar `python -m py_compile app/api/views.py`.
- [ ] Si hay servidor en Docker/Windows, reiniciar o esperar `watchmedo`; un server viejo puede seguir sirviendo rutas antiguas.

### 7.4 Pagos — SSoT (`payment`)

- `payment/cod/` — Contra entrega, `CodCommands`
- `payment/nequi/` — Nequi Push, `NequiCommands`

```python
# CORRECTO — logica post-aprobacion (SSoT para TODO metodo de pago)
from payment.shared.commands import confirm_order_payment
confirm_order_payment(order)  # idempotente: retorna sin mutar si order.status == 'paid'

# CORRECTO — inicializar pago Wompi
from payment.online.services.commands import WompiCommands
wompi_tx = WompiCommands.initialize_transaction(order)

WOMPI_SECRET = settings.WOMPI_EVENTS_SECRET  # nombre correcto en settings
```

**`confirm_order_payment` es idempotente:**

```python
# payment/shared/commands.py
@transaction.atomic
def confirm_order_payment(order):
    order = Order.objects.select_for_update().get(pk=order.pk)
    if order.status == 'paid':
        return   # ya procesado — salida temprana
    _deduct_inventory_for_order(order)
    order.status = 'paid'
    order.save()
    transaction.on_commit(lambda: dispatch_notification(...))
```

**Metodos de pago disponibles (Order.PAYMENT_METHOD_CHOICES):**

### 7.6 Inventario (Stock) — SSoT

`inventory` es la unica fuente de verdad para stock. Ninguna app puede habilitar venta/renta/servicio sin un `StockRecord` activo con cantidad >= 1.

```python
# CORRECTO — verificar disponibilidad via SSoT
from inventory.services.selectors import InventorySelector

if InventorySelector.get_stock_for_variant(variant) < quantity:
    raise ValueError("Sin existencias disponibles.")

# CORRECTO — registrar salida
from inventory.services.commands import InventoryCommands
stock_record = StockRecord.objects.get(content_type=ct, object_id=variant.uuid, is_active=True)
InventoryCommands.register_exit(
    stock_record=stock_record,
    quantity=quantity,
    reference=f"Order {order.uuid}"
)

# INCORRECTO — nunca modificar stock directamente
variant.stock -= quantity  # Prohibido
variant.save()

# INCORRECTO — InventorySelector.is_available() no existe
InventorySelector.is_available(variant)  # Metodo inexistente — usar get_stock_for_variant()
```

**Regla:** Si no existe `StockRecord` para una variante, `get_stock_for_variant()` retorna `0` (no True/bypass). El admin DEBE crear el registro en `/panel/inventario/` antes de que el cliente pueda comprar.

### 7.7 Motor de Precios (Quotes — PricingEngineSelector)

`quotes.AdditionalCost` es la SSoT para todos los costos adicionales (impuestos, descuentos, transporte, logistica, operacional, setup). Nunca hardcodear impuestos o descuentos en otras apps.

```python
# CORRECTO — calcular precio final con costos adicionales
from quotes.services.selectors import PricingEngineSelector  # lazy import recomendado

breakdown = PricingEngineSelector.calculate_price_breakdown(
    variant,
    base_price=Decimal(str(variant.price)),
    quantity=quantity,
)
# breakdown dict:
# {
#   'base_price': Decimal,
#   'quantity': int,
#   'base_subtotal': Decimal,
#   'costs': [{'name', 'context', 'cost_type', 'value', 'amount', 'is_discount'}],
#   'total_additions': Decimal,
#   'total_discounts': Decimal,
#   'final_price': Decimal,
# }

# Atajo si solo necesitas el precio final:
final = PricingEngineSelector.get_final_price(variant, base_price, quantity)
```

**Reglas:**
- Las apps que llaman a `PricingEngineSelector` DEBEN usar lazy imports (`from quotes... import` dentro del metodo) para evitar dependencias circulares.
- `CostAssignment` usa GenericFK (`ContentType + object_id=uuid`) identico al patron de `StockRecord`. No crear tablas de junction separadas.
- `applies_globally=True` → el costo se suma automaticamente a todas las variantes sin asignacion especifica.
- Snapshots (`QuotationItemCostSnapshot`, `OrderItemCostSnapshot`) son inmutables: cambios futuros en `AdditionalCost` no afectan historico.

**Endpoints BFF admin:**
- `GET/POST /api/v1/dashboard/additional-costs/` — listado y creacion
- `PATCH /api/v1/dashboard/additional-costs/{uuid}/update/` — actualizacion parcial
- `POST /api/v1/dashboard/additional-costs/{uuid}/deactivate/` — soft-delete (204)
- `POST /api/v1/dashboard/additional-costs/{uuid}/assign/` — asignar a variante especifica
- `GET /api/v1/shop/variants/{uuid}/price-breakdown/?quantity=N` — desglose publico (AllowAny)

### 9.1 N+1 Queries (Prohibido)

```python
for p in products:
```

### 14.2 Validacion de Cupones

Validar SIEMPRE temporalidad y capear el descuento. `active=True` solo NO es suficiente.

```python
from django.utils import timezone

now = timezone.now()
coupon = Coupon.objects.filter(
    code=coupon_code,
    active=True,
    valid_from__lte=now,
    valid_to__gte=now,
).first()
if not coupon:
    raise ValidationError("El cupon no es valido o ha expirado.")
if coupon.is_percentage:
    discount = (total_items_price * coupon.discount_value) / 100
else:
    discount = coupon.discount_value
discount = min(discount, total_items_price)   # cap: descuento no puede superar el total
```

## 15. PRINCIPIOS DE EJECUCIÓN IA (KARPATHY PRINCIPLES)

> Fuente: [karpathy-guidelines.mdc](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/.cursor/rules/karpathy-guidelines.mdc)
> `alwaysApply: true` — Rigen **toda** interacción de IA en este repositorio sin excepción.
>
> **Compensación fundamental:** Estos principios priorizan la cautela sobre la velocidad.
> Para tareas triviales, usar el criterio propio.

---

### Principio 1 — Think Before Coding (Piensa antes de codificar)

**No asumas. No ocultes la confusión. Expón los compromisos.**

Antes de implementar cualquier cosa:

- Declara tus suposiciones explícitamente. Si no estás seguro, **pregunta**.
- Si existen múltiples interpretaciones, preséntelas — no elijas en silencio.
- Si existe un enfoque más simple, dilo. Cuestiona cuando sea justificado.
- Si algo no está claro, **detente**. Nombra qué es confuso. Pregunta.

```
ANTES de escribir código:
  "Entiendo que quieres X. Asumo Y. ¿Es correcto?"
  "Veo dos interpretaciones: A o B. ¿Cuál es la correcta?"
  "Hay una forma más simple de hacer esto: Z. ¿La prefieres?"
```

---

### Principio 2 — Simplicity First (Simplicidad ante todo)

**El mínimo código que resuelve el problema. Nada especulativo.**

- Sin características más allá de lo solicitado.
- Sin abstracciones para código de un solo uso.
- Sin "flexibilidad" o "configurabilidad" no pedida.
- Sin manejo de errores para escenarios imposibles.
- Si escribes 200 líneas y podrían ser 50, reescríbelo.

**Pregúntate:** *"¿Un ingeniero senior diría que esto es innecesariamente complicado?"*
Si la respuesta es sí — simplifica.

```python
# MAL: Sobre-ingeniería no solicitada
class ProductPriceCalculatorFactory:
    def create_calculator(self, strategy: str) -> AbstractCalculator: ...

# BIEN: Lo mínimo que resuelve el problema
def get_price(variant):
    return variant.discounted_price or variant.price
```

---

### Principio 3 — Surgical Changes (Cambios Quirúrgicos)

**Toca solo lo que debes. Limpia solo tu propio desorden.**

Al editar código existente:

- No "mejores" código, comentarios o formato adyacente.
- No refactorices cosas que no están rotas.
- Mantén el estilo existente, aunque lo harías diferente.
- Si notas código muerto no relacionado, **menciónalo** — no lo borres.

Al crear cambios que generan huérfanos:

- Elimina imports/variables/funciones que **tus cambios** dejaron sin uso.
- No elimines código muerto pre-existente salvo que se pida explícitamente.

**El test:** Cada línea cambiada debe trazarse directamente a la solicitud del usuario.

```
Solicitud: "Agregar campo phone_number a UserProfile"

CORRECTO: Solo agregar el campo + migración + serializer field
INCORRECTO: Agregar el campo + "ya que estoy, refactorizo el selector" 
            + "mejoro el formato de este método" + "elimino este import viejo"
```

---

### Principio 4 — Goal-Driven Execution (Ejecución orientada a objetivos)

**Define criterios de éxito. Itera hasta verificar.**

Transforma tareas en objetivos verificables:

| Tarea vaga | Objetivo verificable |
|-----------|---------------------|
| `"Agrega validación"` | `"Escribe tests para entradas inválidas, luego hazlos pasar"` |
| `"Arregla el bug"` | `"Escribe un test que lo reproduzca, luego hazlo pasar"` |
| `"Refactoriza X"` | `"Asegura que los tests pasan antes y después"` |

Para tareas de múltiples pasos, declara un plan breve:

```
1. Agregar campo `phone_number` a UserProfile → verificar: migración sin errores
2. Exponer en UserProfileSerializer → verificar: GET /api/v1/auth/profile/ retorna campo
3. Permitir actualización en PATCH → verificar: test de update exitoso
```

Criterios de éxito fuertes permiten iterar independientemente.
Criterios débiles (`"que funcione"`) requieren aclaración constante.

---

### Resumen ejecutivo (aplicar en cada tarea)

```
ANTES de codificar:
  [ ] Declare suposiciones y pide confirmación si hay ambiguedad
  [ ] Identifica si hay un enfoque mas simple disponible
  [ ] Define el criterio de exito verificable

DURANTE la implementacion:
  [ ] Toca solo los archivos y lineas necesarias para la tarea
  [ ] Mantiene el estilo del codigo circundante
  [ ] No agrega features, abstracciones ni refactors no pedidos

DESPUES de implementar:
  [ ] Verifica que el criterio de exito se cumple
  [ ] Elimina solo los huerfanos que tus cambios generaron
  [ ] Reporta cualquier codigo muerto pre-existente que notes (sin borrarlo)
```

> **Estos principios funcionan cuando:** los diffs tienen menos cambios innecesarios,
> hay menos reescrituras por sobrecomplicacion, y las preguntas de clarificacion
> llegan ANTES de la implementacion — no despues de los errores.

### 18.1 Split de Commands/Selectors: grep el proyecto ENTERO, no solo la app tocada

Al mover una clase de `services/selectors.py` a `services/commands.py` (o viceversa), otros
modulos que la importaban (`core/api/internal_ai.py`, `core/api/views.py`,

funcionando); falla en runtime cuando otro archivo hace `from core.services.selectors import
HomeFeedSelector` y esa clase ya vive en `commands.py`. Causo una caida real de TODOS los
endpoints (incluido login) sin que ningun test lo detectara antes.

### 18.2 `.annotate()` con el mismo nombre de un `@property` sin setter

Si un Selector hace `.annotate(total_services_completed=Count(...))` y el modelo ya tiene
`@property def total_services_completed(self): ...` SIN `@total_services_completed.setter`,
Django lanza `AttributeError` al materializar la fila (`setattr(instance, name, value)`), no
lo ignora silenciosamente. Caso real: `ContractorAdminSelector.list_all_for_admin()` vs.
`UserProfile.total_services_completed`.

```python
# CORRECTO: el setter cachea el valor anotado; el getter lo prioriza si existe
@property
def total_services_completed(self):
    if '_total_services_completed' in self.__dict__:
        return self.__dict__['_total_services_completed']
    return self.services_as_technician.filter(status='completed').count()

@total_services_completed.setter
def total_services_completed(self, value):
    self.__dict__['_total_services_completed'] = value
```

Antes de agregar un `.annotate(nombre=...)` nuevo, `grep` el modelo por `def nombre` — si es
una `@property` existente, agregarle el setter en el mismo cambio.

### 18.3 `UniqueConstraint` / `unique_together` nuevo exige auditar serializers por `instance=`

DRF `ModelSerializer` genera automaticamente un `UniqueTogetherValidator` desde
`Meta.constraints`/`unique_together`. Si la vista instancia el serializer SIN `instance=`
(ej. `Serializer(data=data, partial=True)` en vez de `Serializer(instance, data=data,
partial=True)`), DRF trata la request como creacion y exige TODOS los campos de la
constraint como requeridos — incluso en un PATCH parcial de un campo no relacionado. Caso
real: al agregar `UniqueConstraint(fields=['document_type', 'document'])` a `UserProfile`,
`AccountViewSet.profile()` empezo a exigir `document_type`/`document` en cada PATCH de
perfil porque no pasaba `instance=`.

```python
# CORRECTO — siempre bindear instance al actualizar
serializer = UserProfileUpdateSerializer(ProfileResolver.resolve(request.user), data=data, partial=True)
```

Ademas: campos `CharField(blank=True, null=True)` guardan `''` (no `None`) cuando se dejan
vacios via `register_user()`. Un `UniqueConstraint(condition=Q(campo__isnull=False))` NO
excluye estos strings vacios — dos usuarios sin documento colisionan igual. Usar
`condition=Q(campo__isnull=False) & ~Q(campo='')`.

### 18.4 `@transaction.atomic` de alcance amplio borra su propio audit trail en un re-raise

Si una funcion completa esta envuelta en `@transaction.atomic` y su bloque `except` escribe
un registro de auditoria (`TransactionEvent`, `SecurityEvent`, etc.) y luego hace
`raise`/re-lanza la excepcion, TODO el atomic block (incluida la escritura de auditoria) hace
rollback — el registro de error desaparece completo, justo el caso que mas se necesita
loguear. Caso real: `WompiCommands.initialize_transaction`. Fix: envolver en `atomic` SOLO
las escrituras que deben ser todo-o-nada; dejar el bloque de error-logging + re-raise FUERA
del atomic (o en su propio `with transaction.atomic():` acotado).

### 18.5 Migraciones: nombres de indice/constraint limitados a 30 caracteres

`name=` en `models.Index`/`UniqueConstraint` esta limitado a 30 caracteres (Django system
check E034) sin importar el motor de base de datos. Verificar longitud ANTES de correr
`makemigrations`; si la migracion ya se genero pero no se aplico, editar el nombre en el
archivo de migracion directamente en vez de generar una migracion de rename.

### 18.6 Nunca correr dos `manage.py test` en paralelo

Dos invocaciones de `manage.py test` (una en foreground, una en background) contra el mismo
proyecto usan la MISMA base de datos de test — se corrompen mutuamente (recreate-on-conflict)
y producen decenas de errores falsos que parecen regresiones de codigo pero son contencion de
infraestructura. Verificar que no hay un test corriendo en background antes de lanzar otro.

`DELETE /api/v1/users/{uuid}/erase/` hacia `user.delete()` (hard delete) directo, sin
capturar excepciones, violando la regla ya establecida en la seccion 6.1 de este documento
("Nunca hacer DELETE fisico... usar soft-delete"). Auditoria completa (2026-07-17) confirmo
que **ninguna** FK directa a `User` usa `PROTECT`/`RESTRICT` en todo el proyecto — y aun
asi `user.delete()` lanzaba `django.db.models.deletion.ProtectedError` sin control (500).
La razon: Django's deletion `Collector` recorre TODO el grafo de cascada, no solo el primer
nivel. `RentalRequest.user` es CASCADE (nivel 1), pero `RentalOperation.rental_request` es
PROTECT (nivel 2) — al intentar cascadear el borrado de `User` hacia su `RentalRequest`,
Django encuentra que esa `RentalRequest` esta protegida por una `RentalOperation` y aborta
con `ProtectedError`. Un `grep` de "FK directa a X con PROTECT" NO es suficiente para
auditar si un hard-delete de X es seguro — hay que recorrer el grafo completo (cualquier
modelo que dependa, aunque sea indirectamente via CASCADE, de X).

**Regla:** antes de hacer hard-delete de cualquier modelo con FKs entrantes, o (mejor)
nunca hacerlo — usar `is_deleted=True` (`SintelBaseModel`, ya heredado por `User` y las
otras 16 apps). Si de verdad se necesita un hard-delete real en algun caso futuro, auditar
el grafo COMPLETO de cascada (no solo las FKs directas) y envolver en
`try/except (ProtectedError, IntegrityError)` -> respuesta HTTP controlada (409), nunca
dejar que se propague como 500.

### 18.12 `basename=` de un DRF router NO define el path — un 404 de frontend puede ser un simple mismatch de string

`orders/api/urls.py` registra `router.register(r'addresses', ShippingAddressViewSet,
basename='shipping-address')`. El path real es `/api/v1/orders/addresses/` (el primer
argumento posicional), pero `basename` solo nombra el reverse-URL interno de DRF
(`shipping-address-list`, etc.) — no aparece en ninguna URL real. `CustomerAddressView.vue`
llamaba `orders/shipping-addresses/` (calcado del `basename`, no del path real) en sus 4
requests y recibia 404 en las 4. **Antes de asumir "falta un endpoint", grep el `r'...'`
literal del `router.register()` correspondiente** — el bug mas comun de este tipo es
copiar el `basename` (con guion y en plural) en vez del primer argumento del `register()`.

**Bug relacionado, mismo fix (2026-07-17):** `ShippingAddressSerializer.validate()` tenia
un chequeo de campos requeridos (`full_name`/`address_line_1`/`city`) incondicional, que
rompia cualquier `PATCH` parcial que no los incluyera (ej. `{"is_default": true}` para
marcar una direccion como predeterminada). Regla ya conocida de DRF pero reincidente: un
`validate()` override que exige un campo SIEMPRE debe distinguir `if field in attrs` (creacion
o el campo vino en el PATCH) de `elif not self.partial` (solo exigir en creacion/PUT
completo) — nunca asumir que `attrs` trae todos los campos del modelo.

### 18.13 Llamar la raiz de un router DRF en vez del sub-recurso: `v-for` sobre un objeto no truena, itera sus valores (bug silencioso)

Encontrado durante la unificacion del design system de "Mi Cuenta" (2026-07-17), via
Playwright, no reportado por el usuario: `CustomerQuotesView.vue` llamaba
`api.get('quotes/', {...})` en vez de `api.get('quotes/quotations/', {...})` (el resto del
proyecto — `QuotationList.vue`, `quotesService.js`, `CatalogSummaryStep.vue` — siempre usa
`quotes/quotations/`). `quotes/api/urls.py` registra VARIOS routers (`quotations`,
`quote-template-categories`, `quote-template-subcategories`, `quote-templates`) bajo el
mismo prefijo `quotes/`, asi que `GET /api/v1/quotes/` sin el sub-recurso devuelve la vista
raiz de DRF: un dict plano de hyperlinks (`{"quotations": "http://.../quotations/", ...}`),
**200 OK**, no 404 — el bug no se anunciaba con un error de red.

El efecto real: `res.data.results` no existe en ese dict (undefined) -> el codigo caia al
fallback `res.data` (el dict completo) -> `quotes.value` quedaba como ESE OBJETO, no un
array. `quotes.length === 0` es `undefined === 0` (false), asi que el estado vacio nunca se
mostraba. Y `v-for="quote in quotes"` sobre un objeto en Vue 3 **itera sus valores** (aqui,
las URLs string) en vez de tirar un error de "no iterable" — cada "quote" terminaba siendo
un string, y `quote.uuid.slice(...)` en el template reventaba con `TypeError` al primer
render, atajado por el `ErrorBoundary` (pantalla en blanco sin sidebar, sin mensaje util).

**Regla derivada:** cuando un router DRF expone multiples sub-recursos bajo el mismo
prefijo, un llamado a la raiz sin el sub-recurso NUNCA falla con 404 — devuelve 200 con el
indice de hyperlinks, y solo se detecta si el codigo de consumo asume una forma de dato
que no es un array (aqui, silenciosamente, via `v-for` sobre un objeto). Antes de confiar
en `api.get('<app>/')`, verificar contra otro archivo del proyecto que YA consuma el mismo
recurso (grep `'<app>/<recurso>'`) en vez de asumir que el prefijo del app basta.
